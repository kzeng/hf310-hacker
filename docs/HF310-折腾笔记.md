### 2.1 一个容易踩的坑

`/system/priv-app/ufilauncherzx.apk` —— 厂商把**中兴微风格的 UFI 启动器**塞进了高通板子的系统里。

这解释了为什么网上拆机帖会说 HF310 是"中芯微/中兴微"：**同一型号混装不同方案**。网络上关于 HF310 的资料互相矛盾，原因就在这里。本机经多重证据确认是高通 MSM8916：

- `ro.board.platform = msm8916`
- `/proc/cpuinfo` 四核 Cortex-A53
- ModemManager 读出 `M8916EAAAANVZM` 基带固件
- USB 暴露 `qmi_wwan` + `cdc-wdm2`

### 2.2 支持的频段（ModemManager 读出）

- LTE：B1 / B2 / B3 / B5 / B7 / B8 / B20 / B39 / B40
- UMTS：B1 / B2 / B5 / B8
- 当前配置：LTE B1 / B3 / B5
- ModemManager 状态：`failed (sim-missing)`
  - 原因：内置 eSIM 由设备自己的服务管理，QMI 层看不到；**不是故障**

## 2.3 拆机实录（2026-11-15，照片见 webwxgetmsgimg1/2.jpeg）

### 板号

**`MZ702_V1.0`**，生产日期 **2022-09-30**（丝印在板边，`BOT`/`BOOT` 字样旁边）

### 主要元件

| 器件 | 丝印 | 说明 |
|---|---|---|
| SoC | `QUALCOMM MSM8916 5VV B4R200.0 K144500` | 骁龙 410，K1445 = 2014 年第 45 周 |
| 存储 | `SKhynix H9TP32A4GDCC PRKGM 549Y` | eMMC + LPDDR3 二合一封装，4GB + 512MB（与 df/meminfo 一致） |
| 射频 | `WTR3905` | 高通收发器 |
| 电源 | `QVV 58335 156R2 2221T` | PMIC 类器件 |

### 三个关键发现

**① 板边有一排测试排针（金手指圆点）**

标签自上而下：`UIM1` / `DD` / `VBUS` / `GND` / `Flash` / `VPH_PWR` / `1P8` / `LS_1P8` / **`BOOT`** / `TX` / `RX`

- `BOOT` + `TX`/`RX` = 标准的**启动模式跳线 + 1.8V UART 调试口**
- 意味着**进 9008 不一定需要盲猜短接点**，也意味着有串口控制台可用
- `UIM1` = SIM 接口引出

**② SIM 卡座区域引出了 USIM 测试点**

卡座下方丝印：`U_RES` / `U_DATA` / `U_CLK` / `U_VREG` / `GND`，并排 5 个金色测试焊盘。

→ 即使卡座不可用，也能直接焊线外接 SIM，不必飞线猜引脚。

**③ 天线端有一颗实体轻触按键**

位置在远离 USB 的天线一侧，旁边丝印 `BOOT`。大概率是复位/启动键。
外壳若有开孔，以后不用拆机就能按住它进 9008。

### 卡座与内置卡

- 卡座为金属壳 + 黑塑料，顶部贴黄标：**ICCID `<ICCID_REDACTED>`**（19 位）
- 外壳标签上的 `898612221908087700` 与板载贴纸**不一致**，以板载贴纸为准
- 系统内 `gsm.sim.operator.numeric = 46011` → **中国电信**，与 `898611` 前缀吻合
- `gsm.sim.state = READY`，但 `gsm.network.type = Unknown`、`gsm.operator.alpha` 为空
  → **SIM 在位且就绪，但没有注册上网**（未激活/未实名/套餐未生效，或数据服务未开）

### 厂商线索

- `persist.sys.juzhen.type = ufi`、`persist.sys.juzhen.ssid.prefix = 4G-UFI-`、`persist.sys.juzhen.wifi.password = <FACTORY_WIFI_PASSWORD>`
  → SSID/密码就存在 `build.prop` 里，可直接改
- 后台首页标题：**`UFI配置管理 - ZHXL_V2.0.0`**
- Web 服务是 `ufilauncherzx.apk`（已加固，libjiagu）在 80 端口起的本地服务
- API 前缀：`loginInfo/` `system/` `wifi/`（如 `loginWithPwd`、`getSettings`、`getDeviceType`）
- 已拉取的 APK / build.prop / props 在 `/tmp/opencode/hf310/`

### 重要：MZ702 不是社区已知板号

社区有现成 Debian/OpenWrt 移植的板号是：
`UFI001B/C`、`UFI003`、`UFI103S_V05`、`UF629_V1.1`、`UZ801`、`UFI16_V3`、`QRZL903-1`、`MF32T_MB_V01`

**`MZ702_V1.0` 不在其中。** 硬件参数完全一致（MSM8916 + 512MB + 4GB），但缺少对应的 device tree / boot.img 端口，直接套用别人固件的风险显著高于“照抄教程”。

## 3. 核心结论

**这台是高通 410 平台，能刷机。**

- ✅ 可刷 Debian 11/12、OpenWrt（酷安 @苏苏小亮亮 / @jsbsbxjxh66 那批 MSM8916 固件）
- ✅ 有 **9008 EDL** 可救砖（`05c6:9008`）
- ✅ 可 root（Magisk patch boot.img）
- ✅ 可当纯 4G 模块（QMI），插路由器做 CPE
- ✅ 无电池 → 插充电头可 7×24 挂机，比电池机更适合当小服务器
- ✅ 可改 IMEI（QXDM / QCN）、可锁频段

**但有个前提没说清**：社区固件按**板号**分包（UFI003_MB_V002 / UFI103S_V05 / UF629_V1.1 之间互刷有讲究，有人刷完开不了机）。本机外壳封死，**必须拆开看板上丝印**才能定刷哪一包。

## 4. 三条路线

### A. 不刷机，只折腾系统（风险低）
- 装 `su`、跑 Debian chroot（rootfs 放 /data）
- 关掉 `ufilauncherzx` 的云控上报、替换后台
- 缺点：Android 4.4.4 + 512MB，跑什么都紧

### B. 刷 Debian / OpenWrt（主流玩法，中风险）
```
备份 → 拆壳看板号 → 选镜像 → fastboot 刷 → 换基带(QCN) → SSH 192.168.68.1
```
- 好处：SSH、root、跑 sing-box / alist / nginx，插电长期在线
- 代价：原厂 0.9 元 100G 套餐作废，需自备流量卡；刷错要 9008 救

### C. 当纯 4G 模块 / CPE（最省事）
- 切到 `rndis` 模式，插 OpenWrt 路由器 USB 口当 WAN，可做双卡负载均衡
- 不改系统，随时还原

## 6. 已完成的操作记录

### 6.1 修复 ADB 权限（udev）

问题：`adb devices` 报 `no permissions (missing udev rules?)`，因为系统 udev 规则只覆盖 `18d1`(Google) 和 `2717`(小米)，没有高通的 `05c6`。

解决（已执行）：

```bash
sudo tee /etc/udev/rules.d/51-android-05c6.rules >/dev/null <<'EOF'
# Qualcomm 05c6 - HF310 / MSM8916 UFI
SUBSYSTEM=="usb", ATTR{idVendor}=="05c6", MODE="0666", GROUP="plugdev"
EOF

sudo udevadm control --reload-rules && sudo udevadm trigger --subsystem-match=usb
```

修复后：`adb devices` → `0  device usb:1-2.3 product:UFI model:UFI device:UFI transport_id:1`

### 6.2 用到的诊断命令


- **改 IMEI 在国内违法**（《电信条例》禁止伪造、冒用电信码号）
- 刷机后原厂内置 eSIM 套餐（0.9 元/100G）作废；内置卡为**中国电信**（46011）

- **MZ702_V1.0 无社区固件**，直接刷 UFI003/UFI103S 等镜像很可能开不了机
- 禁止在未备份、未确认板号的情况下刷任何固件包
- 未主动执行 `adb reboot bootloader` / `adb reboot edl`（避免变砖风险）

## 10. 板型确认：MZ702 就是 jz0145-v33（2026-11-15）

### 10.1 破解方法

原厂 `boot.img` 里带着高通官方 MTP 设备树，解出来对比社区 DTS 即可。

```
boot.img 头: page_size=2048, dt_size=0x47800
内含 2 个 FDT:
  dtb_0  144338 B  model "MSM 8916 MTP"        board-id 0x8
  dtb_1  144070 B  model "MSM 8916 512MB MTP"  board-id 0x8,0x100
```

### 10.2 引脚对照（决定性证据）

| 功能 | MZ702 原厂 DT | jz0145-v33 | ufi001c |
|---|---|---|---|
| reset 键 | **37** | **37** | 37 |
| led r/g/b | **8 / 6 / 7** | 6 / 7 / 8 | 22 / 21 / 20 |
| sim1_switch | **22** | esim-sel gpio22 | gpio0 |
| sim2_switch | **23** | esim-sel gpio23 | gpio3 |
| sim3_switch | **1** | sim-en gpio1 | gpio1 |
| sim_hotdet | **20** | sim-sel gpio20 | gpio2 |

→ LED 三脚和 SIM 四脚全部命中 `jz0145-v33`，只是 LED 的 r/g/b 命名顺序不同。

### 10.3 后果

**不需要移植 device tree。** `OpenStick-Builder` 仓库自带 `dtbs/msm8916-jz01-45-v33.dtb`
（`model = JZ01-45-V33 4G Modem Stick`，`compatible = thwc,ufi001c`），改一下 `configs/extlinux.conf` 的 `fdt` 行即可。

## 11. EDL 打通记录（关键成果）

### 11.1 原厂 fastboot 是废的

```
fastboot getvar  → OK
                → Sending 'xx' OKAY, Writing 'xx' FAILED (unknown command)
reboot / continue / erase / oem * → unknown command
```

原厂 LK 0.5 只实现了 `getvar` 和 `download`。**刷机必须用 lk2nd 的 fastboot**（先 EDL 写 aboot）。

### 11.2 进 9008

`adb reboot edl` 可直接进（无需短接）。USB 变为 `05c6:9008`。

### 11.3 loader 匹配（踩坑点）

```
HWID    : 0x007050e100000000 (MSM8916)
PK_HASH : cc3153a80293939b90d02d3bf8b23e0292e452fef662c74998421adad42a380f
```

`bkerler/edl` 自带的 msm8916 loader 全是别的哈希，匹配不上。要用同一个签名钥匙的：

```
qualcomm/factory/msm8916/007060e100000000_cc3153a802939b90_fhprg_peek.bin
```

存为 `/tmp/opencode/hf310/loaders/l8916_cc3153a8.bin`（93188 B，ELF32 ARM）。

```bash
python3 /tmp/opencode/edl/edl.py --loader=<该文件> printgpt
```

### 11.4 两个必知细节

- **Sahara 的 HELLO 只在 USB 枚举时发一次**。一旦某次握手失败，后续所有读取都是缓冲区陈旧数据，表现为反复 `Timed out` 或同样的 `RX:04000000...`。**必须物理拔插重来**，软件层 RESET / USB reset 都救不回来（USB reset 甚至会让设备直接从总线上掉线）。
- EDL 成功后 firehose 常驻，后续 `edl.py` 调用会直接检测到 firehose 模式，不需要重复进 9008。

## 13. 刷机实录（2026-11-15，成功）

### 13.1 关键认知：原厂 sbl1 跑不了 lk1st

第一次只写了 `aboot`（= lk1st），复位后**设备完全不枚举**（不 9008、不 Android）。
写回读校验证明数据没问题（前 322540 字节与 `aboot.mbn` 逐字节相同）。
真实原因是**整套启动链必须一起换**：刷入 DB410c 底包的 `sbl1/tz/rpm` + `qhypstub`（hyp）后，lk1st 立刻起来了。

### 13.2 生成适配真实磁盘的 GPT

`files/gpt_both0.bin` 是 **179MB 假磁盘** 的模板（`last-lba=350208`，`rootfs` 只有 1MB），
而且它是 fastboot 专用格式（primary 34 扇区 + backup 条目 + backup 头拼在一起）。
本机 `0x748000` 扇区，必须重新生成并拆成三段写：

```
N = 0x748000 (7634944 扇区)
primary  (MBR+头+128 条目)  → sector 0
backup 条目 (32 扇区)       → sector N-33 = 7634911
backup 头   (1 扇区)        → sector N-1  = 7634943
```

分区布局沿用模板，只把 `rootfs` 拉到磁盘末尾（`348194..7634910` = 3.47GiB）。
**`boot` / `rootfs` 的 PARTUUID 必须保留**，否则 `extlinux.conf` 的 `root=` 和 `/etc/fstab` 都对不上：

```
boot   80780b1d-0fe1-27d3-23e4-9244e62f8c46
rootfs a7ab80e8-e9d1-e8cd-f157-93f69b1d141e
```

### 13.3 全量 EDL 刷写（绕过 fastboot）

```bash
L=/tmp/opencode/hf310/loaders/l8916_cc3153a8.bin
python3 edl.py --loader=$L ws 0        gpt_primary.bin
python3 edl.py --loader=$L ws 7634911  gpt_backup_entries.bin
python3 edl.py --loader=$L ws 7634943  gpt_backup_header.bin
for n in sbl1 tz rpm hyp aboot; do python3 edl.py --loader=$L w $n $n.mbn; done
python3 edl.py --loader=$L w boot   /tmp/opencode/osb/boot.raw      # 注意：必须转 raw，不能直接写 sparse
python3 edl.py --loader=$L w rootfs /tmp/opencode/osb/rootfs.raw
for n in fsc fsg modem modemst1 modemst2 persist sec; do python3 edl.py --loader=$L w $n $n.bin; done
```

写入后抽读校验：`aboot` 全分区 / `sbl1` 前 253KB / `boot` 前 4MB / `rootfs` 中部与尾部 —— 全部逐字节一致。

### 13.4 第二个坑：按键误判导致进 fastboot

刷完后 lk1st 起来了（`18d1:d00d`），但每次重启都停在 fastboot。日志（`fastboot oem log` + `get_staged`）给出：

```
[50] Detected device: uz801 v3.0 4G Modem Stick
[70] ERROR: No recovery partition found
[70] ERROR: Could not do normal boot. Reverting to fastboot mode.
```

链路是：`keys_get_state(KEY_VOLUMEUP)` 为真 → `boot_into_recovery=1` → 跳过 `lk2nd_boot()` → 找 `recovery` 分区 → 没有 → fastboot。

因为构建脚本写死了 `LK2ND_COMPATIBLE="yiming,uz801-v3"`，而该设备数据库条目把重启键定义在 **GPIO23（低电平有效）**——那是本板的 SIM2 检测脚，默认被拉低，等于「一直按着键」。

本板真正的匹配项是 `thwc,ufi001c`（按键只有 GPIO37 的 `edl` 键，与本板 reset 键一致）：

```bash

     LK2ND_COMPATIBLE="thwc,ufi001c" TOOLCHAIN_PREFIX=arm-none-eabi- lk1st-msm8916
python3 src/qtestsign/qtestsign.py aboot build-lk1st-msm8916/emmc_appsboot.mbn -o files/aboot.mbn
fastboot flash aboot files/aboot.mbn
```

## 15. 配网热点 + captive portal + mDNS（2026-11-15）

### 15.1 行为

| 场景 | 行为 |
|---|---|
| 开机有可用上行（已知 WiFi / 蜂窝） | 不开热点，只跑 mDNS + SSH |
| 开机没有任何上行 | 先扫一遍周围 WiFi（缓存到磁盘）→ 拉起热点 `Openstick`（`192.168.4.1`）→ 提供配网页 |
| 配网页提交成功 | NetworkManager 切到 STA，热点自动关闭，守护进程停止监听 |

### 15.2 部署的文件

| 路径 | 作用 |
|---|---|
| `/usr/local/bin/openstick-provisiond` | 配网守护进程（Python 3 标准库，无第三方依赖） |
| `/etc/systemd/system/openstick-provision.service` | `Restart=always`，`After=NetworkManager` |
| `/etc/NetworkManager/dnsmasq-shared.d/00-captive.conf` | 只劫持各平台联网检测域名 → `192.168.4.1`，触发自动弹窗 |

### 15.3 踩到的四个坑（都在代码里规避了）

| 坑 | 现象 | 解法 |
|---|---|---|
| `wcn36xx` 在 AP 模式不支持扫描 | `iw scan` → `Operation not supported (-95)` | 拉热点**之前**先扫一遍，结果存磁盘，页面用缓存渲染 |
| `nmcli device wifi connect <SSID>` 依赖扫描结果 | AP 模式下报 `No network with SSID 'xxx' found`（rc=10） | 改为直接 `nmcli con add type wifi ... ` 建配置再 `con up`，不依赖扫描 |
| 单射频，AP 与 STA 互斥 | 连上 WiFi 时热点必然消失 | 状态机里 `uplink` 一旦出现就主动 `con down hotspot` |
| 提交表单后热点立刻消失 | 成功页面返回不到浏览器 | 改为异步连接 + 立即返回“连接中”页，页面每 2s 轮询 `/status` |
| 守护进程可能在 STA 切换中途又把 AP 拉起来 | 连不上/反复跳 | 提交后设 90 秒“连接保护期”，失败立即解除 |
| 刚开机时射频才初始化，扫描只出 4 个网络 / 缓存为空 | 配网页列表空白，看着像坏了 | 扫描带重试（最多 3 次）；AP 模式下缓存不足且**没有客户端连着**时，短暂拆热点扫一次再拉回（5 分钟一次上限）；实在为空则提示直接手输 SSID |

## 17. frp 内网穿透 + 外网 SSH（2026-11-15）

### 17.1 架构

```
[任意设备] --ssh:31022--> [kzeng nginx stream 0.0.0.0:31022]
                              └--> 127.0.0.1:26222 (frps 回环)
                                    └--> frpc 隧道 --> [HF310 :22]
```

- kzeng（47.97.193.62）frps 保持 `proxyBindAddr = "127.0.0.1"`（回环加固，8080/8081 只走 nginx HTTPS）
- 内部端口 **26222**（frpc remotePort），公网端口 **31022**（nginx stream）
- 两个端口必须不同：nginx 无法在 frps 已占用 `127.0.0.1:<port>` 时再 bind `0.0.0.0:<同 port>`（EADDRINUSE）

### 17.2 HF310 侧

- frpc 二进制：`frp 0.71.1 linux_arm64`（本机是 **aarch64**，不是 32 位！）→ `/usr/local/bin/frpc`
- 配置：`/etc/frp/frpc.toml`（token 同 kzeng frps，见 `/etc/frp/frps.toml`）
  - proxy `hf310-ssh`：`localIP 127.0.0.1 / localPort 22 / remotePort 26222`
- 服务：`/etc/systemd/system/frpc.service`，`systemctl enable --now frpc`（开机自启 + 断线重连）

### 17.3 kzeng 侧

- `frps.toml` allowPorts 增加 `{ start = 26222, end = 26222 }`
- nginx 顶层加 `stream {}` 块 + `/etc/nginx/stream.d/hf310-ssh.conf`：`listen 31022; proxy_pass 127.0.0.1:26222;`

### 17.4 使用

| sysfs | GPIO | DT `color`/`function` | **实际颜色** | 逻辑名 |
|---|---|---|---|---|
| `red:power` | TLMM 8 | red / power | 红 | `red` |
| `green:wlan` | TLMM 7 | green / wlan | **蓝** ⚠️ | `blue` |
| `blue:wan` | TLMM 6 | blue / wan | **绿** ⚠️ | `green` |

> **DT 的颜色标注是错的**：`green:wlan` 那颗实际是蓝灯，`blue:wan` 那颗实际是绿灯。2026-11-15 逐个点亮校准确认（看到顺序 红 → 蓝 → 绿）。
> 所以代码里用 `LED_MAP` 把逻辑颜色映射到 sysfs，物理接线变了只改这一处：

```python
LED_MAP = {
    "red":   "/sys/class/leds/red:power/brightness",
    "green": "/sys/class/leds/blue:wan/brightness",    # 物理绿灯
    "blue":  "/sys/class/leds/green:wlan/brightness",  # 物理蓝灯
}
```

另有 `mmc0::`（eMMC 活动灯，`trigger=mmc0`，max_brightness=255），是 sdhci 注册的，不动它。

手动控制（注意文件名是 DT 名，不是实际颜色）：

```bash
echo 1 | sudo tee /sys/class/leds/blue:wan/brightness     # 亮的是绿灯
echo 0 | sudo tee /sys/class/leds/green:wlan/brightness   # 灭的是蓝灯
```

校准方法（每颗单独亮 5 秒，肉眼记录）：

```bash
sudo sh -c 'systemctl stop hf310-led
for l in red:power green:wlan blue:wan; do echo 0 > /sys/class/leds/$l/brightness; done
for l in red:power green:wlan blue:wan; do
  echo ">>> $l"; echo 1 > /sys/class/leds/$l/brightness; sleep 5
  echo 0 > /sys/class/leds/$l/brightness; sleep 1
done
systemctl start hf310-led'
```

### 19.2 状态约定

| 状态 | 触发条件 | 红灯 | 绿灯 | 蓝灯 |
|---|---|---|---|---|
| `boot` 启动中 | 还没有状态文件 | 常亮（有电） | 慢闪 1Hz | 灭 |
| `online` **正常** | 有上行 + 外网可达 | **灭** | **常亮** | 灭 |
| `no-internet` 外网不通 | 有上行，但 TCP 探测失败 | 慢闪 1Hz | 常亮 | 灭 |
| `ap` 配网模式 | 无上行，热点已开 | 灭 | 蓝绿交替 1Hz | ← 交替 |
| `connecting` 连接中 | 提交配网后 90s 内 | 灭 | 快闪 4Hz | 灭 |
| `error` 服务异常 | `state.json` 超 30s 未更新 | 灭 | 灭 | 快闪 4Hz |

一句话记法：

- **只有绿灯常亮** = 一切正常
- **绿常亮 + 红慢闪** = 网连上了但上不了外网（查上游/欠费）
- **绿蓝交替闪** = 在等你配网
- **只蓝灯快闪** = 配网服务挂了

### 19.2.1 外网可达性探测

LED 守护进程里有个后台线程，每 15 秒 **TCP 连一次公共 DNS**（`223.5.5.5:53`、`119.29.29.29:53`，各 3 秒超时），不依赖 DNS 解析，也不 ping（ICMP 常被墙/限速）。

```python
NET_TARGETS = (("223.5.5.5", 53), ("119.29.29.29", 53))
NET_POLL = 15.0
```

探测放在独立线程，绝不阻塞闪烁节拍（`socket.create_connection` 最长堵 3 秒，放主循环里灯会卡住）。

### 19.4 坑：闪烁频率与刷新节拍必须整除

第一版 `TICK = 0.25`，4Hz 快闪（半周期 0.125s）**完全不闪** —— 每次刷新都恰好落在“亮”的相位上，被混叠掉了。

```python
TICK = 0.125     # 必须能被闪烁半周期整除
```

改后实测（按**实际颜色**采样，顺序 红/蓝/绿，0.08s 一次）：

```
boot         100 100 100 100 101 101 101     红常亮 + 绿 1Hz
online       001 001 001 ...                 只有绿灯常亮
no-internet  101 101 101 101 001 001 001     红 1Hz + 绿常亮（绿不闪）
ap           010 001 001 001 010 010 010     绿/蓝 交替 1Hz
connecting   000 001 000 001 000 001 001     绿 4Hz
error        010 010 000 010 010 000 000     蓝 4Hz
```

> `no-internet` 的验证方式：临时加一条 nft 规则 drop 掉到 `223.5.5.5/119.29.29.29:53` 的出站包，模拟断网，测完 `nft delete table inet ledtest` 清掉。
> 状态文件停更 30 秒会自然跳到 `error`（停 provisiond 时正好能顺便验证）。
